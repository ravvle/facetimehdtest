# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pure-Bash installer that gets the Apple FaceTime HD camera (Broadcom BCM1570, PCI `14e4:1570`) working on 2013–2015 Intel MacBooks under Ubuntu 22.04/24.04/26.04, Fedora 44 and AlmaLinux 10. It builds the `facetimehd` driver via DKMS, extracts the Apple firmware, and optionally makes sure `mbpfan` is installed and running so the fans stop throttling. It configures no power management at all - see "Power management" below. The internal keyboard needs nothing from this project: `hid_apple` ships in the kernel on every supported distribution and loads itself.

The driver built by this project is [src/facetimehd/](src/facetimehd/), a
maintained fork of `patjak/facetimehd` commit `364b1c663583`, with its changes
documented in [src/facetimehd/DOWNSTREAM.md](src/facetimehd/DOWNSTREAM.md).
[driver-patches/](driver-patches/) holds that same change set as a generated,
numbered patch series against the upstream tree - useful for review or for
proposing individual changes upstream. It is an output of `DOWNSTREAM.md`,
not an input to anything: nothing in `scripts/`, `tests/` or CI reads it, and
it is regenerated by hand when the fork moves rather than kept in sync
automatically.

## Commands

```bash
# Lint (exactly what CI runs - see .github/workflows/ci.yml)
shellcheck -x --source-path=SCRIPTDIR \
    setup.sh \
    scripts/install.sh scripts/uninstall.sh scripts/macbook-tune.sh \
    scripts/extract-firmware.sh scripts/collect-diagnostics.sh \
    packaging/build-deb.sh packaging/build-rpm.sh \
    tests/build-driver.sh tests/smoke-capture.sh \
    tests/hw-validate.sh tests/script-smoke.sh
# scripts/lib/common.sh is only sourced, never listed directly - shellcheck -x
# follows it from whatever sources it. Every other tracked *.sh must appear in
# that list; CI has a step that fails if one does not.

# Installer plumbing that shellcheck structurally cannot see. No root, no
# hardware, no network - safe to run anywhere.
./tests/script-smoke.sh

# Compile src/facetimehd against every headers tree present
./tests/build-driver.sh
./tests/build-driver.sh 7.0.0-14-generic      # one kernel only
KDIR=/path/to/headers ./tests/build-driver.sh # an unpacked headers package
CC=gcc-14 ./tests/build-driver.sh             # pin the compiler
LLVM=1 W=1 WERROR=1 ./tests/build-driver.sh   # strict Clang build
SPARSE=1 W=1 ./tests/build-driver.sh           # Sparse semantic checks

# Exercise the installed driver on real hardware (needs a MacBook + v4l-utils)
sudo ./tests/smoke-capture.sh                 # leaves the module loaded
sudo ./tests/smoke-capture.sh --unload        # remove it afterwards
./tests/smoke-capture.sh --no-load            # module already loaded, no root

# Validate the things only hardware can confirm - one section per open item in
# src/facetimehd/DOWNSTREAM.md "Validation"
sudo ./tests/hw-validate.sh                   # all but the reboot test
sudo ./tests/hw-validate.sh --only probe,timing
sudo ./tests/hw-validate.sh --skip suspend    # laptop in use, or headless
sudo ./tests/hw-validate.sh --reboot          # reboots; re-run after to read the verdict

# Firmware extraction on its own (install.sh calls this; --no-install needs no root)
./scripts/extract-firmware.sh --no-install
sudo ./scripts/extract-firmware.sh [--dest DIR] [-x DRIVER_FILE] [-i]

# Are Apple's downloads still there and still what the checksum tables expect?
# Installs nothing, needs no root. This is what the weekly CI watchdog runs.
./scripts/extract-firmware.sh --check-sources

# Distribution packages (both write to packaging/out/)
./packaging/build-deb.sh
./packaging/build-rpm.sh

# One-file bug report, redacting the DMI serial and UUID
./scripts/collect-diagnostics.sh

# Sensor calibration (.dat) files - a separate Apple download, needs unar
sudo ./scripts/extract-firmware.sh --calibration-only
sudo ./scripts/extract-firmware.sh --calibration-only --sys /path/AppleCamera.sys

# Single entry point: asks which of the below to run, then runs it
sudo ./setup.sh [-y]

# Install / uninstall (require root)
sudo ./scripts/install.sh [-y|--force|--skip-firmware|--skip-hw-check]
sudo ./scripts/install.sh --enroll-mok          # Secure Boot signing key
sudo ./scripts/install.sh --runtime-pm off      # persist facetimehd.runtime_pm=0
sudo ./scripts/install.sh --no-load              # install without touching the live module
./scripts/install.sh --status                   # what is installed; needs no root
sudo ./scripts/uninstall.sh [--keep-tuning]

# Make sure mbpfan is installed and running (requires root)
# Not configured - it ships a sane fan curve - this just installs/enables it.
sudo ./scripts/macbook-tune.sh [--revert|--skip-fan]
```

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs shellcheck, an executable-bit check on `setup.sh`, `scripts/*.sh`, `tests/*.sh` and `packaging/*.sh`, the script smoke test, both package builds, the Apple-download watchdog, the driver build across Ubuntu 22.04/24.04/26.04 + Fedora 44 + AlmaLinux 10, and strict Clang and Sparse analysis — on every push and weekly on a schedule. The weekly run is the point: it catches breakage with nobody touching the repo.

**There are two ways this project breaks without anyone touching it, and each has a watchdog.** The build matrix catches a new kernel dropping an API the driver uses. The `apple-sources` job catches the other half: the firmware and calibration both come from Apple-hosted URLs with SHA-256 tables in `extract-firmware.sh`, and if Apple retires or republishes either, every new install breaks and the first anyone would otherwise know is a bug report. It downloads ~4 MB, verifies it, and writes nothing — no Apple content is stored, so it is a checksum comparison rather than a redistribution. It is skipped on pull requests, because a fork's CI has no business hammering Apple's CDN and a failure there is never caused by the diff under review.

Fedora is in the matrix because it carries the newest kernel of anything tested, so kernel API churn lands there first. AlmaLinux 10 is there for the opposite reason: an Enterprise Linux kernel sits on 6.12 for a decade while Red Hat backports into it, so it catches code that assumes an API newer than the oldest supported kernel — and it catches version checks that an EL backport has quietly falsified. Both RPM jobs pass `KDIR=/usr/src/kernels/<ver>` to `build-driver.sh`, because `kernel-devel` unpacks there and a container has no `/lib/modules/<ver>/build` symlink to follow.

## Architecture

**[setup.sh](setup.sh) is a menu, not a place for logic.** It asks two yes/no
questions (driver? fan support?) and calls `scripts/install.sh` and/or
`scripts/macbook-tune.sh` with `-y` if it got one itself. It has no options of
its own beyond `-y`/`--help` and does not know about `--skip-firmware`,
`--revert`, or anything else the scripts it calls support - those are reached
by running that script directly. Keep it that way: logic belongs in the
script that owns the thing being configured, not in the entry point in front
of it.

**The maintained driver source is included.** The fork lives under
[src/facetimehd/](src/facetimehd/) and installing does not fetch source from
GitHub. The one networked project step is firmware extraction from Apple's
servers, because that firmware cannot legally be redistributed.

**Sensor calibration is a second, independent download.** The `NNNN_01XX.dat`
set files fix the camera's colours and exist *only* in the Windows Boot Camp
driver — the OS X kext does not carry them, so the firmware download cannot
supply them. `extract-firmware.sh` range-fetches just the
`AppleCamera64.exe` member out of the 542 MB `bootcamp5.1.5769.zip` (~1.2 MB),
inflates it with a synthesised gzip header rather than a zip tool, unpacks the
solid RAR with `unar`, and carves the four files at offsets keyed by the
SHA-256 of `AppleCamera.sys` — which is the *same* hash table the firmware path
already uses, because it is the same file. Each carved file is SHA-256 verified,
so a wrong offset installs nothing. `unrar-free` cannot read solid RAR3 and is
not a substitute. The camera works without all of this, so `install.sh` treats
every failure here as a warning.

**Firmware extraction is ours** ([scripts/extract-firmware.sh](scripts/extract-firmware.sh)). It is derived from `patjak/facetimehd-firmware`, which died in 2020, and is maintained here under GPL-2.0-only. It downloads a byte range of an Apple-hosted OS X 10.11.5 update, carves the firmware out of the `AppleCameraInterface` kext, and SHA-256-verifies both the kext and the image. Only firmware 1.43.0 actually works.

**Version derivation** ([scripts/install.sh](scripts/install.sh)): `PACKAGE_VERSION` is read out of `src/facetimehd/dkms.conf`. A fingerprint of `src/facetimehd/**/*.{c,h}` + `Makefile` is appended as `+d<hash>`, then the staged copy under `/usr/src/` gets its `dkms.conf` rewritten to match.

**Idempotency**: `install.sh` copies `src/facetimehd/` to a temporary tree, diffs that against `/usr/src/facetimehd-<version>` (excluding `dkms.conf`), and skips the rebuild when they match and DKMS reports installed. `uninstall.sh` discovers every registered DKMS version rather than assuming one.

**Shared shell layer**: [scripts/lib/common.sh](scripts/lib/common.sh) is sourced, never executed — output helpers (`info`/`step`/`warn`/`error`/`die`/`ok`/`bad`, NO_COLOR-aware), `require_root`/`have`/`require_cmds`/`confirm` (honours `ASSUME_YES`), `detect_os`/`is_debian_like`/`is_rpm_like`, the package layer below, `has_facetimehd_hardware`, `firmware_root`, systemd probes. New scripts source it and get shellchecked with `-x --source-path=SCRIPTDIR`.

**Package abstraction**: `pkg_manager`/`pkg_refresh`/`pkg_install`/`pkg_installed`/`pkg_available` wrap apt and dnf. They abstract the *verbs* only — package names differ per family and stay in the calling script, because that is where the reason for each name lives. `pkg_available` exists to tell "not installed yet" apart from "not packaged for this distro at all"; that distinction is what lets `macbook-tune.sh` exit cleanly on a derivative with no mbpfan package instead of dying on a package-manager error, and it is what keeps a missing `unar` on Enterprise Linux from failing an otherwise fine driver install.

**EPEL, on Enterprise Linux**: `is_enterprise_linux`/`el_major_version`/`dnf_repo_enabled`/`enable_crb`/`ensure_epel` in `common.sh`. Red Hat ships no DKMS, so `install.sh` (dkms) and `macbook-tune.sh` (mbpfan) both need EPEL turned on; `ensure_epel` is the one place that knows how. It is the deliberate exception to "the package layer abstracts verbs, not names" — "enable EPEL" *is* a verb, `epel-release` is spelled the same on every rebuild, and splitting it would put the same three-repository dance in two files. Everything about it is best-effort and advisory: a failure warns and continues, because the `pkg_install` that follows is what actually discovers a missing package and it names the package, which is more useful than anything guessed earlier. `is_enterprise_linux` must exclude Fedora by `ID` *first*, since AlmaLinux sets `ID_LIKE="rhel centos fedora"` and would otherwise match on the `fedora` arm.

**Secure Boot is opt-in, not automatic** ([scripts/install.sh](scripts/install.sh), section 2b). Under Secure Boot an unsigned module builds perfectly and then refuses to load, which reads as "the installer worked and the camera is broken" — so the installer detects it and, with `--enroll-mok`, generates a Machine Owner Key, records it in `/etc/dkms/framework.conf` and hands it to `mokutil`. It cannot be automatic: `mokutil --import` needs a password typed at a prompt and the enrolment is only completed by a human at MokManager on the next boot. The key paths are read from `framework.conf` when set and otherwise default to each family's own (`/var/lib/shim-signed/mok/MOK.*` on Debian, `/var/lib/dkms/mok.*` elsewhere), so this never creates a second key competing with the distribution's. It runs *before* the DKMS build, because DKMS signs at build time.

**`--status` is the diagnostic entry point.** It reports hardware, DKMS, module, firmware, calibration, Secure Boot, device node and runtime-PM state, with a `fix:` line for each failure, and needs no root — so it is dispatched before `require_root`. Anything it cannot read as a normal user is reported as unknown rather than as a failure. `scripts/collect-diagnostics.sh` is its long form: one file to attach to an issue, with the DMI serial and UUID redacted. The redaction is deliberately narrow — a filter aggressive enough to catch anything serial-shaped would eat PCI IDs and kernel versions, which are the point of the report.

**Packaging is a second front door, not a replacement** ([packaging/](packaging/)). `build-deb.sh` (dpkg-deb from a staging tree, no debhelper) and `build-rpm.sh` + `facetimehd-dkms.spec.in` produce a `facetimehd-dkms` package that installs the driver source and registers it with DKMS. They deliberately do not fetch the firmware: a post-install script that reaches the network breaks offline installs and image builds, and the firmware is Apple's and unredistributable either way — so the packages ship `facetimehd-firmware-install`, a wrapper the user runs once, and the post-install script says so loudly. Nor do they touch Secure Boot, which needs a console and a reboot. The package version is `PACKAGE_VERSION` with **no** source fingerprint appended, unlike `install.sh`: the fingerprint exists so a rebuild from an edited working tree cannot reuse a version, and a package is a fixed artefact whose version is already in its filename.

**Fan support is deliberately its own script** ([scripts/macbook-tune.sh](scripts/macbook-tune.sh)), not part of `install.sh`. `mbpfan` is not coupled to the camera — the camera works without it, and it works on a Mac with no camera driver — so the camera installer does not change unrelated system behaviour by default; it only points at the script. The script installs and enables `mbpfan`; it does not configure it, because its own fan curve is reasonable for this hardware. State (whether it enabled `mbpfan.service` itself) lives under `/var/lib/facetimehd/`, so `--revert` only disables the service if this script was the one that turned it on. `uninstall.sh` delegates that to `macbook-tune.sh --revert` rather than reimplementing it. `hid_apple` needs nothing at all: it ships in the kernel and loads itself.

**The runtime-PM drop-in is the one modprobe file this project writes.** The full installer defaults to `--runtime-pm on`; `--runtime-pm off` is the recovery opt-out. Both write `/etc/modprobe.d/facetimehd-runtime-pm.conf`, both refresh the initramfs because this PCI driver can load before the real root filesystem, and `uninstall.sh` removes the project-owned file.

**Power management beyond this camera is not this project's job.** The driver implements its own runtime PM (see [src/facetimehd/DOWNSTREAM.md](src/facetimehd/DOWNSTREAM.md), "Power management"): real `dev_pm_ops`, with the full-device transition selected by `facetimehd.runtime_pm=1`. The module default stays off so bare module discovery does not schedule an ISP/DDR/PCI teardown, while the full installer explicitly enables the validated path. Every supported distribution already ships a power daemon that never touches this camera's PCI runtime PM, USB autosuspend or PCIe ASPM (`power-profiles-daemon` on Ubuntu, TuneD on Fedora), so there is nothing else for this project to configure.

## Deliberate decisions

There is no `docs/` tree: the project's prose lives in `README.md`,
`CONTRIBUTING.md`, `SECURITY.md`, `packaging/README.md` and the two files under
`src/facetimehd/`. Anything pointing at `docs/*.md` is stale — treat it as the
README's "Troubleshooting and support" section and fix the path while you are
there. Read the following before "fixing" any of it:

- **No top-level `dkms.conf`.** The authoritative one is `src/facetimehd/dkms.conf`; a second copy only drifts.
- **The firmware checksum tables live in one place** — [scripts/extract-firmware.sh](scripts/extract-firmware.sh). They were upstream's; they are now ours to maintain. Do not copy them into `install.sh` or the docs.
- **No driver version or kernel version anywhere in the scripts.**
- **A change to `src/facetimehd/` is not done until `DOWNSTREAM.md` says why.** The fork has no patch headers to carry that reasoning instead, so this is the review record for its changes. `driver-patches/` is a generated view of that same record, not a second place to explain anything.
- **This project configures no power management, and does not configure mbpfan.** See the "Fan support" and "Power management" paragraphs above for why `macbook-tune.sh` only installs and enables rather than writing config, and why nothing here touches PCI runtime PM, USB autosuspend, ASPM or a power-profile daemon. Do not reintroduce a fan curve, a `hid_apple` modprobe drop-in, or a TLP/power-profile drop-in without a concrete problem the upstream defaults don't solve.
- **`hid_apple` is not this project's concern at all any more.** It ships in the kernel on every supported distribution and loads itself; there is nothing to install, check, or configure, so `macbook-tune.sh` no longer touches it.
- **Runtime PM is enabled by the full installer and remains disabled by the module's bare default.** It is validated on the current driver over repeated runtime cycles and suspend-while-streaming. The build that hard-locked the validation MacBook froze with runtime PM disabled too, so do not misattribute that regression to power management. `--runtime-pm off` remains the recovery path.
- **A requested runtime-PM setting must be followed by an initramfs refresh.** On affected MacBooks, initramfs udev can load `facetimehd` before the real root and its `/etc/modprobe.d` are mounted. DKMS refreshes the image before `install.sh` writes or removes its drop-in, so the installer explicitly refreshes it again afterward; otherwise `--runtime-pm off` can silently take effect too late.
- **The DDR/PLL bring-up messages are `dev_dbg`, not `dev_info`** — and the same goes for `FWMSG`, the firmware's own console. They read like once-per-boot banners, but runtime PM re-runs `fthd_hw_init()` on *every* resume, so at `dev_info` they wrap a default kernel ring buffer in a minute or two and evict everything else, including the driver's own suspend records. Probe prints one `dev_info` summary line instead; `dyndbg=+p` brings the detail back. Failure messages were moved the other way, `dev_info` → `dev_err`.
- **Debugfs is created in `probe()` and destroyed in `remove()`, never across a suspend.** `debugfs_create_devm_seqfile()` is devm-managed, and runtime PM makes a suspend/resume cycle happen every few idle seconds, so tearing the tree down and rebuilding it each time leaks a devres entry. The accessors take a runtime-PM reference instead — reading one powers the camera up.
- **The whole project is GPL-2.0-only.** `scripts/` was MIT until 2026-08, when absorbing the GPL-2.0-only firmware extractor into `scripts/extract-firmware.sh` required relicensing the lot. Derived code must keep its upstream attribution header — do not quietly reword provenance away.
- **`diffutils` is in the RPM dependency list on purpose.** It is Essential on Debian and so never listed there, but a minimal Fedora has no `diff` at all — and the rebuild-skip in `install.sh` is a `diff -rq` whose failure is swallowed. Without it the installer silently loses idempotency and rebuilds every run.
- **`install.sh` splits its dependencies into required and best-effort, and the split is not arbitrary.** A compiler, make, dkms, kmod, cpio, curl, gzip, xz, `diffutils` and `elfutils-libelf-devel` are what build and install the driver: failing to get one is fatal. `pciutils`, `v4l-utils` and `unar` are not — they power the hardware check, the closing verification advice and the sensor calibration respectively. Losing one of those costs a diagnostic or the camera's colours, never a working camera, so refusing to install over it would be wrong. `unar` is still installed wherever it exists and the calibration step still runs on every install that has it; it is only whether it is *available* that varies, because it comes from EPEL on Enterprise Linux and EPEL does not rebuild every Fedora package for every EL release.
- **`curl` is only named as an RPM dependency when `/usr/bin/curl` is actually missing.** The RPM families' default installs carry `curl-minimal`, which already provides the binary, and `dnf install curl` *conflicts* with it rather than upgrading it. Listing `curl` unconditionally therefore breaks the entire dependency step on a stock AlmaLinux or Fedora system — a whole-install failure caused by a package that was already there.
- **EPEL is enabled on the way in and left alone on the way out.** `uninstall.sh` does not remove it: by then other packages may depend on it, and tearing out a system-wide repository is a far more surprising thing for a camera uninstaller to do than leaving one enabled.
- **Do not restore the removed inferred firmware controls from `953fe61`–`8e154f9`.** That series repeatedly hard-locked the MacBookAir7,2 after probe. Static analysis of firmware `S2ISP-01.43.00` proved that AE bias and AWB CCT submitted short payloads, test-pattern put its value in the wrong halfword, AWB gain was structurally wrong, and chroma suppression was not a one-value control. The old opt-in gates were removed with the interfaces: a module parameter is not adequate containment for a command capable of freezing the host. Read `src/facetimehd/FIRMWARE-REVERSE-ENGINEERING.md` before implementing any of them. Keep stream-resume, frame-decimation and mutable-crop work available for independent validation.
- **A recovered firmware value may reach V4L2 as a read-only control; a firmware *setter* may not.** `v4l2_ctrl_handler_setup()` skips read-only controls, so registering one adds a GET and no SET the framework can replay at `STREAMON` or after a runtime resume — which is the exact mechanism behind the lockups above. `awb_cct_estimate` (`FTHD_CID_AWB_CCT_ESTIMATE`) is the first and is private rather than `V4L2_CID_WHITE_BALANCE_TEMPERATURE`, because that standard control means the temperature an application asks the camera to assume and there is still no validated way to write one. `tests/script-smoke.sh` asserts the read-only flag; do not drop it to "make the control settable".
- **The ISP's semi-planar output is NV12, not NV16, and that came from hardware.** Upstream's 2015 comment called format code 0 "plane 0 Y plane 1 UV" without a sampling; everyone since, this repo included, filled in 4:2:2. A capture showed a `width*height` luma plane followed by exactly `width*height/2` of chroma, with Cb/Cr matching a YUYV capture of the same scene to within 0.2. `sizeimage` is `width * height * 3 / 2`; the 4:2:0 sizing is the part that must not regress, because reading chroma over a 4:2:2 extent averages it with unwritten zeros and reports a number that looks like a wrong format. Do not reintroduce NV16: no output-format code produces it.
- **NV12 is the default format, and "the default" is three things that must agree.** `ENUM_FMT` index 0, what `fthd_v4l2_adjust_format()` coerces an unsupported request to, and the `pixelformat` probe stores before registering the node. `tests/script-smoke.sh` asserts all three agree. YUYV is the only other format: YVYU (ISP code 2) writes invalid chroma and must stay unreachable, which the smoke test also asserts. Every parser in `tests/hw-validate.sh` that reads pixels assumes a packed layout, so `mean_luma()` and the metering section call `use_packed_format` first, per capture - reloading the module puts the device back on its default. The `WARN_ON` fallback in `fthd_start_channel()` deliberately uses the packed code, not the default: it is reached with `bytesperline` computed for a packed frame.
- **`CISP_CMD_CH_OUTPUT_CONFIG_SET`'s `x2` is the destination row stride, not "chroma size".** Upstream hardcoded `width * 2`, which for the packed formats is both a correct stride and an unremarkable constant — the two readings were indistinguishable until a one-byte-per-pixel plane arrived and the ISP wrote luma rows at double spacing, leaving half the frame blank. It raised **no** IOMMU fault: the ISP skips rows rather than overrunning, so `sizeimage` still covered it and the corruption was silent. Pass `bytesperline`; for YUYV/YVYU that is `width * 2` and the command is unchanged.
- **`CISP_CMD_CH_CROP_SET` is `(x, y, width, height)`, and the crop must stay on the sensor.** Firmware accepts a window that leaves the array and then delivers no frames until it reloads; `S_SELECTION` is reachable by any local user, so that would let one application deny the camera to all. `fthd_v4l2_set_crop()` clamps the origin to `sensor - size` and rounds `left` *down* to 8 - rounding up could push it back off. The width is a multiple of 8, which also rules out the odd-width-at-odd-offset sensor fault; `fthd_isp_cmd_channel_crop_set()` refuses both as a last line. Until `S_SELECTION` sets a crop it follows the format (`CROP_DEFAULT`, the largest centred window at the output aspect); setting `CROP_DEFAULT` hands it back. `tests/script-smoke.sh` asserts the wire layout and the clamp, and `hw-validate.sh --only crop-geometry` probes the edges.
- **`S_PARM` decimates; it does not program the ISP's AE frame-rate window.** The window is held at 30 fps (`30 * 256`, Q8.8). Upstream drives `S_PARM` and `EXPOSURE_AUTO_PRIORITY` through it, but whether it changes the delivered rate is unmeasured here, and a reported rate the stream does not match stalls `pipewiresrc`. Measure before adopting either.
- **A test that checks only size and exit status cannot tell these formats apart.** Both the false NV16 pass and the blank-row bug survived such a check. `v4l2-ctl` also exits 0 when `VIDIOC_STREAMON` fails, printing the error to stdout — so captures must be judged by whether the file holds a complete frame, and semi-planar formats by inspecting the luma and chroma planes separately against a YUYV reference of the same scene.
